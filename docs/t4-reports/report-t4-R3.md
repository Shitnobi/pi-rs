## [HIGH] `cancel_autocomplete_request` never aborts the suspended continuation — cancelled requests resurrect on the next flush

- **TS**: editor.ts:2287-2322 (`requestAutocomplete` → `cancelAutocompleteRequest`), editor.ts:2444-2452 (`cancelAutocompleteRequest` does `this.autocompleteAbort?.abort()`), editor.ts:2416-2430 (`isAutocompleteRequestCurrent` starts with `!controller.signal.aborted &&`).
- **Rust**: `editor.rs:756-763` (`cancel_autocomplete_request`) and `editor_autocomplete.rs:116-134` (`run_pending_autocomplete_requests`), `editor_autocomplete.rs:442-462` (`abort_in_flight_autocomplete`).
- **What TS does**: every cancel path (Escape, Up/Down history keys, `setText`, `setAutocompleteProvider`, `submitValue`, paste, re-request) aborts the in-flight request's `AbortController`. When the provider promise later resolves, the continuation's currency gate sees `signal.aborted` and discards the result — a cancelled request can never show/apply suggestions. **Verified empirically**: provider with a 120ms-pending promise; type `@mai`, wait 50ms (request started, controller armed), press Up arrow (historyPrevious → `cancelAutocomplete`, empty history → state unchanged), wait for the provider to resolve, `flushAutocomplete()` → `isShowingAutocomplete() === false`. Control run without the cancel shows `true`.
- **What Rust does**: `cancel_autocomplete_request` only bumps the start token, clears the debounce timer and the pending queue, and pointlessly resets the `autocomplete_aborted` flag (see finding #5). It does **not** touch the thread-local `IN_FLIGHT` continuation. `run_pending_autocomplete_requests` *unconditionally* runs whatever `IN_FLIGHT` holds (editor_autocomplete.rs:120-122) before touching the pending queue. The continuation's gate (`editor_autocomplete.rs:252-267`) checks `signal.aborted()` (never set at cancel time) and `is_autocomplete_request_current` — which passes whenever no *newer request has started* and text/line/col still match the snapshot. So a cancelled request whose snapshot still matches is resurrected and **applies its suggestions**.
- **Concrete repro** (mirrors the verified TS scenario): provider returns `[{value:"@main.ts",...}]`; `set_autocomplete_provider`; type `@mai`; `editor.tick_autocomplete_debounce(20)` (request starts, provider called, continuation suspended with snapshot `"@mai"`); press Up arrow with empty history (`handle_input("\x1b[A")` → `cancel_autocomplete`, state unchanged); `editor.run_pending_autocomplete_requests()` → Rust: `is_showing_autocomplete() == true` (menu resurrected from the cancelled request). TS: stays `false`. Even worse variant: if the cancelled request was `force && explicit_tab` with a single item, the resurrected continuation *auto-applies the completion and mutates the text* (editor_autocomplete.rs:285-315) — TS can never do this after a cancel. Same divergence via `set_autocomplete_provider(new)` after a tick: the flush applies the OLD provider's captured result while `autocomplete_provider` is the new one.
- **Why ported tests miss it**: the Rust tests flush before cancelling (e.g. `escape_cancels_active_autocomplete` in editor_input.rs:661-664 shows the menu first, which consumes `IN_FLIGHT`), so the resurrection path is never exercised.
- **Suggested fix**: in `cancel_autocomplete_request` (editor.rs:756), call `self.abort_in_flight_autocomplete()` after bumping the token (mirroring editor.ts:2448), so the suspended continuation is aborted-and-dropped at cancel time exactly like TS. The `start_autocomplete_request` lazy-abort call then becomes a no-op safety net.

## [MED] Abort is observable only at the *next request start*, not at cancel time — TS aborts synchronously at the re-requesting keystroke

- **TS**: editor.ts:2294 (`requestAutocomplete` runs `cancelAutocompleteRequest()` synchronously before scheduling) + editor.ts:2448. **Verified empirically**: abort-listening provider (editor.test.ts:2661-2696 shape); type `@mai`, wait 50ms (request in flight), type `n` → `aborts === 1` *immediately*, before the new 20ms debounce fires.
- **Rust**: `editor_autocomplete.rs:171-180` — `start_autocomplete_request` performs the abort ("aborts lazily at the next request start", per its own comment), and `run_autocomplete_request` aborts lazily when the gate fails. Nothing aborts at `request_autocomplete`/keystroke time.
- **What Rust does wrong**: after the re-requesting keystroke but before the new debounce fires (or before a flush), the previous request's `AbortSignal` is still not aborted. A provider observing `signal.aborted()` at that point (or a test asserting `aborted_signal_count()` right after `handle_input("n")` without ticking) sees 0 in Rust vs 1 in TS. The Rust port of the TS abort test (`aborts_active_at_autocomplete_when_typing_continues`, editor_autocomplete.rs:1383-1410) masks this by asserting only *after* `tick_autocomplete_debounce(50)`.
- **Concrete repro**: same setup as the TS abort test, but assert `provider.aborted_signal_count()` immediately after `editor.handle_input("n")` (before any tick): Rust 0, TS 1.
- **Suggested fix**: same as finding #1 — abort in `cancel_autocomplete_request`. That also makes the abort observable at exactly the TS points (every `requestAutocomplete`, every explicit cancel).

## [MED] Single `IN_FLIGHT` thread-local slot: starting a request on a second editor silently drops the first editor's in-flight request

- **TS**: editor.ts:2324-2341 — `autocompleteRequestTask` is a **per-instance** field; each editor's promise chain runs independently.
- **Rust**: `editor_autocomplete.rs:66-70` (`IN_FLIGHT` is one process-wide-per-thread slot) and `editor_autocomplete.rs:217-228` — `start_autocomplete_request` unconditionally overwrites the slot with `*slot.borrow_mut() = Some(...)`. `abort_in_flight_autocomplete` (editor_autocomplete.rs:442-462) only aborts/drops a continuation whose `editor_id` matches the current editor; another editor's continuation is put back — and then immediately clobbered by the overwrite, without being aborted.
- **What TS does**: two editors' in-flight requests coexist; each applies (or discards) independently.
- **What Rust does**: with editors E1, E2 — E1 types `@a` + `tick(20)` (E1's request starts, provider called, continuation stored); E2 types `@b` + `tick(20)` (E2's start overwrites the slot; E1's continuation vanishes un-aborted). `E1.run_pending_autocomplete_requests()` finds nothing (peek filters by `editor_id`) → E1 never shows its menu and its provider's signal is never aborted. TS: both editors show their menus; both signals stay live.
- **Suggested fix**: key `IN_FLIGHT` by `editor_id` (e.g. a `RefCell<HashMap<usize, AutocompleteContinuation>>` with insertion-order/one-per-editor semantics, or abort-and-replace only the *same* editor's slot and keep others), mirroring the per-instance `autocompleteRequestTask`.

## [MED] Single `DEBOUNCE_ELAPSED` slot: interleaved `tick` calls between editors reset each other's accumulated debounce time

- **TS**: one `setTimeout(…, 20)` per editor instance (editor.ts:2297-2301); wall-clock time advances all armed timers independently.
- **Rust**: `editor_autocomplete.rs:69-70` (`DEBOUNCE_ELAPSED: (editor_id, start_token, elapsed)`) and `editor_autocomplete.rs:140-166` (`tick_autocomplete_debounce` resets the slot whenever `state.0 != editor_id`).
- **Divergence**: E1 arms its debounce; `E1.tick(10)`; `E2.tick(10)` (resets the slot to E2); `E1.tick(10)` (resets back to E1, elapsed 10) — neither timer fires, and E2's accumulation was also lost. In TS, 20ms of wall-clock time has elapsed for both editors and both timers fire.
- **Concrete repro**: two editors with `@` providers; interleave `tick(10)` × 2 per editor; Rust: `call_count() == 0` for both after the interleaving (each stuck at 10ms); TS (two real editors, 20ms sleeps): both fire.
- **Suggested fix**: store elapsed time per `(editor_id, start_token)` in a map instead of a single triple, so each editor's armed timer accumulates independently.

## [LOW] `autocomplete_aborted` field is write-only dead state with inverted semantics

- **TS**: editor.ts:344 `autocompleteAbort?: AbortController` — set when a request starts, cleared (`= undefined`) when its result is applied or on cancel; the *signal* is the observable.
- **Rust**: `editor.rs:393` (`autocomplete_aborted: bool`), written `true` at the two lazy-abort sites (editor_autocomplete.rs:265, 457) and reset to `false` in `cancel_autocomplete_request` (editor.rs:759-761 — `if self.autocomplete_aborted { … = false }`, i.e. cancel *clears* the abort flag, the opposite of TS's abort-on-cancel). No code ever reads the field for a decision.
- **Impact**: none today (dead), but it documents the wrong mental model and will mislead future parity work. **Suggested fix**: delete the field (the per-request `AbortSignal` in `AutocompleteContinuation` already models `controller.signal.aborted`), or repurpose it as "an in-flight controller exists" if a flush-surface consumer needs it.

## Verified-parity spot checks (no finding)

- **Token patterns (coordinator's quoted-`@"` fix)**: `autocomplete_token_pattern_test`/`token_matches_at` (editor.rs:300-375) correctly implement editor.ts:256-278. The quoted branch `@"[^"]*` requires no closing quote in BOTH trigger and debounce patterns; when a later `"` exists the branch fails and control falls through to the char-class + `SUFFIX` alternative exactly like regex alternation/backtracking (e.g. `@"foo"bar` matches via `@` + SUFFIX since `"` is not a separator). Debounce excludes `@` from the char class but adds the unquoted `@SUFFIX` alternative. Boundary (`^` or separator char) and wrapper scanning `[([{<\`]*` match `autocompleteBoundaryRegex`/`autocompleteTokenStartSource` (utils.ts:62-63, editor.ts:256-258).

## Summary

5 findings: **1 HIGH** (cancelled autocomplete requests resurrect on flush — missing abort of the in-flight continuation in `cancel_autocomplete_request`), **3 MED** (abort observable only at next request start; single `IN_FLIGHT` slot drops other editors' in-flight requests; single `DEBOUNCE_ELAPSED` slot breaks interleaved multi-editor debounce), **1 LOW** (dead/inverted `autocomplete_aborted` flag). The HIGH and the first MED share one root cause and one fix (abort in `cancel_autocomplete_request`). History, kill ring, undo, token patterns, and the synchronous autocomplete surface are faithful to the TS ground truth.
